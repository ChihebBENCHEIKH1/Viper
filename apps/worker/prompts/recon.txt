## Phase 2: Runtime Component Enumeration

Use ADB to verify and enrich every static finding. Do not trust static analysis alone —
runtime state reveals dynamically registered receivers, runtime permissions, and
components that may behave differently when the app is running.

### 2a: Exported Component Enumeration

```bash
# Comprehensive package dump — captures all resolved components
adb shell dumpsys package {{PACKAGE_NAME}} | grep -A 100 "Activity Resolver"
adb shell dumpsys package {{PACKAGE_NAME}} | grep -A 100 "Service Resolver"
adb shell dumpsys package {{PACKAGE_NAME}} | grep -A 50 "ContentProvider"
adb shell dumpsys package {{PACKAGE_NAME}} | grep -A 50 "Receiver Resolver"

# Permissions declared and requested
adb shell dumpsys package {{PACKAGE_NAME}} | grep -A 30 "declared permissions"
adb shell dumpsys package {{PACKAGE_NAME}} | grep -A 30 "requested permissions"

# Runtime-registered broadcast receivers
adb shell dumpsys activity broadcasts | grep {{PACKAGE_NAME}}
```

### 2b: Component Interaction Testing (ADB Invoke Each Exported Component)

For EACH exported component found, attempt to invoke it via ADB to confirm
reachability and observe behavior:

**Activities:**
```bash
# Launch each exported activity directly
adb shell am start -n {{PACKAGE_NAME}}/.ActivityName
# Observe: Does it launch? Does it require auth? Does it crash?
# Record: accessible without auth = HIGH risk, requires auth = MEDIUM, crashes = note error
```

**Services:**
```bash
# Start each exported service
adb shell am startservice -n {{PACKAGE_NAME}}/.ServiceName
# For bound services, note the interface (AIDL/Messenger)
```

**Content Providers:**
```bash
# Query each content provider
adb shell content query --uri content://{{PACKAGE_NAME}}.provider/
# Try common table names: users, accounts, data, config, tokens
adb shell content query --uri content://{{PACKAGE_NAME}}.provider/users
```

**Broadcast Receivers:**
```bash
# Send broadcast to each exported receiver
adb shell am broadcast -a com.example.ACTION -n {{PACKAGE_NAME}}/.ReceiverName
```

Record the result of EVERY invocation attempt in a structured format:
- Component name, type, invocation command, result (success/denied/crash), observations

### 2c: Authorization Architecture Mapping

Map the complete authorization model of the application:

1. **Permission Guards:** For each exported component, record:
   - Custom permissions declared in manifest (`<permission>` tags)
   - Permission requirements on components (`android:permission` attribute)
   - Protection levels (normal, dangerous, signature, signatureOrSystem)
   - Whether permission is enforced at runtime (check `checkCallingPermission()`)

2. **Authentication Gates:** Identify which activities/endpoints require auth:
   - Launch each protected activity directly via ADB — does it redirect to login?
   - Map the auth flow: LoginActivity → TokenStore → ProtectedActivity
   - Identify token type: JWT, session cookie, custom header, OAuth2 bearer

3. **Authorization Layers:**
   - Client-side checks (Activity-level `if (!isLoggedIn)` redirects)
   - Server-side checks (API returns 401/403 without valid token)
   - Hybrid checks (both client and server enforce)
   - MISSING checks (protected data accessible without any auth)

4. **Role-Based Access:** If the app has user roles:
   - Map which endpoints/components enforce role checks
   - Identify role stored location (JWT claim, local DB, SharedPreferences)

## Phase 3: Injection Source Enumeration

Systematically enumerate all points where external data enters the application.
This feeds the injection vulnerability agent directly.

### 3a: Intent-Based Sources
- Exported activities accepting `getIntent().getExtras()`
- Activities with `onNewIntent()` handlers
- Services processing intent extras in `onStartCommand()`
- Broadcast receivers extracting data from received intents

### 3b: URI-Based Sources
- Content provider URI path segments (user-controlled path components)
- Deep link URL parameters (query string values)
- App link path and query parameters
- `Intent.getData()` URI handling

### 3c: UI-Based Sources
- Text input fields (EditText, SearchView, WebView form inputs)
- File picker results (`onActivityResult` with file URIs)
- Clipboard paste operations
- Voice input / dictation results

### 3d: External File Sources
- Files read from external storage (SD card)
- Downloaded files processed by the app
- Files shared via FileProvider from other apps
- ZIP/archive extraction with user-provided files

### 3e: Network Response Sources
- API response data used in local database queries
- Server-provided URLs loaded in WebViews
- Push notification payloads processed locally
- WebSocket message data used in local operations

## Phase 4: Deep Link and App Link Enumeration

From AndroidManifest.xml AND decompiled source, enumerate ALL deep link schemes:

```bash
# Extract intent filters with VIEW action from manifest
grep -A 10 "android.intent.action.VIEW" {{DECOMPILED_PATH}}/apktool/AndroidManifest.xml

# Test each discovered deep link
adb shell am start -a android.intent.action.VIEW -d "scheme://host/path"
```

For each deep link:
- Scheme (custom vs https)
- Host and path pattern
- Handler activity
- Parameter extraction method (getQueryParameter, path segments)
- Validation applied to parameters before use
- Auto-verify status (app links only)

## Phase 5: API Endpoint Mapping

From decompiled source, map ALL network endpoints:

**Search patterns:**
```bash
# Retrofit annotations
grep -rn "@GET\|@POST\|@PUT\|@DELETE\|@PATCH" {{DECOMPILED_PATH}}/jadx/
# OkHttp / HttpURLConnection URLs
grep -rn "new URL\|HttpUrl\|Request.Builder" {{DECOMPILED_PATH}}/jadx/
# Base URL definitions
grep -rn "BASE_URL\|baseUrl\|base_url\|API_URL" {{DECOMPILED_PATH}}/jadx/
# GraphQL
grep -rn "graphql\|query.*mutation\|apolloClient" {{DECOMPILED_PATH}}/jadx/
# WebSocket
grep -rn "wss://\|ws://\|WebSocket\|newWebSocket" {{DECOMPILED_PATH}}/jadx/
```

For each endpoint, determine:
- HTTP method and full URL (with path parameters)
- Authentication requirement (bearer token, API key, session cookie, none)
- Request body content type and fields
- Whether it transmits sensitive data (credentials, PII, financial, health)
- Certificate pinning status for this domain

## Phase 6: Storage and File System Mapping

```bash
# List all app data directories
adb shell run-as {{PACKAGE_NAME}} ls -laR /data/data/{{PACKAGE_NAME}}/

# SharedPreferences files
adb shell run-as {{PACKAGE_NAME}} ls -la /data/data/{{PACKAGE_NAME}}/shared_prefs/

# Database files
adb shell run-as {{PACKAGE_NAME}} ls -la /data/data/{{PACKAGE_NAME}}/databases/

# Cache and files directories
adb shell run-as {{PACKAGE_NAME}} ls -la /data/data/{{PACKAGE_NAME}}/cache/
adb shell run-as {{PACKAGE_NAME}} ls -la /data/data/{{PACKAGE_NAME}}/files/

# External storage usage
adb shell ls -la /sdcard/Android/data/{{PACKAGE_NAME}}/

# Check backup configuration
adb shell dumpsys package {{PACKAGE_NAME}} | grep -i backup
```
