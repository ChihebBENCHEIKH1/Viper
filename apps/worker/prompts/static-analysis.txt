## Analysis Strategy: Three-Phase Parallel Discovery

### Phase 1: Discovery (3 parallel analysis sub-phases)

Launch these three analysis tracks. Use TodoWrite to create items for each.

#### Track A: Manifest & Component Analysis
□ Decompile APK: `jadx -d {{DECOMPILED_PATH}}/jadx/ {{APK_PATH}}`
□ Extract resources: `apktool d -f -o {{DECOMPILED_PATH}}/apktool/ {{APK_PATH}}`
□ Read and analyze AndroidManifest.xml thoroughly:
  - Package name, version, min/target SDK
  - ALL exported components (activities, services, receivers, providers)
  - For each exported component: intent filters, permission guards, task affinity
  - Permissions requested — identify UNUSED or EXCESSIVE permissions
  - Deep link schemes and app links (intent filters with VIEW action)
  - Backup configuration (`android:allowBackup`)
  - Debug flags (`android:debuggable`)
  - Network security config reference (`android:networkSecurityConfig`)
  - `android:taskAffinity` settings (StrandHogg vulnerability)
  - `android:launchMode` settings (task hijacking)
□ If `network_security_config.xml` exists, analyze it:
  - Cleartext traffic allowed? For which domains?
  - Custom trust anchors? User certificates trusted?
  - Certificate pinning configured? Which domains?

#### Track B: Dangerous Sink Hunter
Systematically search the decompiled source for ALL instances of dangerous sinks.
For each sink found, record: file:line, the sink function, and the enclosing class/method.

**Data Storage Sinks (M9):**
□ `SharedPreferences.edit().putString()` / `putInt()` / `putBoolean()` — plaintext sensitive data?
□ `SQLiteDatabase.execSQL()` / `rawQuery()` / `insert()` — user input in queries?
□ `FileOutputStream` / `FileWriter` — world-readable mode? Sensitive content?
□ `getExternalFilesDir()` / `getExternalStorageDirectory()` / `Environment.getExternalStorageDirectory()` — data on SD card?
□ `Log.d()` / `Log.e()` / `Log.i()` / `Log.w()` / `Log.v()` — sensitive data in logcat?
□ `ClipboardManager.setPrimaryClip()` — sensitive data copied?
□ Room `@Entity` classes — what data is persisted? Encrypted?

**Cryptography Sinks (M10 + M1):**
□ `Cipher.getInstance()` — weak algorithms? DES, RC4, AES/ECB, AES/CBC without MAC?
□ `SecretKeySpec` constructor — hardcoded key bytes?
□ `MessageDigest.getInstance("MD5")` / `"SHA1"` — for security purposes (not checksums)?
□ `KeyStore.getInstance()` — proper Android Keystore usage?
□ `PBEKeySpec` — weak iteration count? (<10000)
□ Hardcoded strings matching: API keys, tokens, passwords, secrets in source AND resources
□ `strings.xml`, `BuildConfig`, `gradle.properties` for secrets

**Authentication Sinks (M3):**
□ Login/registration Activity classes and their validation logic
□ `BiometricPrompt` usage — CryptoObject or boolean-only check?
□ Token storage location (SharedPreferences vs EncryptedSharedPreferences vs Keystore)
□ Session management (expiry, refresh token rotation, revocation)
□ `startActivityForResult()` returning auth state without verification

**Network Sinks (M5):**
□ `HttpURLConnection` / `URL.openConnection()` — HTTP vs HTTPS?
□ OkHttp `OkHttpClient.Builder` — certificate pinner configured?
□ Retrofit `@GET` / `@POST` annotations — base URL protocol?
□ Custom `X509TrustManager` — does it actually validate? (trust-all pattern)
□ Custom `HostnameVerifier` — does it verify? (return-true pattern)
□ WebSocket connections — encrypted (wss://) or cleartext (ws://)?

**Injection Sinks (M4):**
□ ContentProvider `query()` / `insert()` / `update()` / `delete()` — parameterized?
□ `WebView.addJavascriptInterface()` — what methods exposed?
□ `WebView.loadUrl()` / `loadData()` / `loadDataWithBaseURL()` — user-controlled URL?
□ `WebView.evaluateJavascript()` — user input in JS string?
□ `Runtime.getRuntime().exec()` / `ProcessBuilder` — user input in command?
□ Deep link handlers — parameter validation before use in operations?
□ `Intent.getStringExtra()` used directly in SQL, file paths, or URLs?

#### Track C: Third-Party & Binary Analysis
□ Identify all third-party libraries (from import statements, lib/ directory, build files)
□ Note versions where identifiable (from filenames, metadata, version constants)
□ Flag known vulnerable libraries (especially: libwebp, OpenSSL < 1.1.1, okhttp < 4.x)
□ Check for React Native (`index.android.bundle`, `libhermes.so`)
□ Check for Flutter (`libflutter.so`, `flutter_assets/`)
□ Check for Cordova (`assets/www/cordova.js`)
□ Check for Xamarin (`assemblies/` directory)
□ Assess ProGuard/R8 obfuscation (are class/method names readable?)
□ Check for root detection implementations
□ Check for tampering/integrity detection
□ Check for emulator detection

### Phase 2: Vulnerability-Focused Backward Taint Analysis

For EACH dangerous sink found in Track B, perform backward taint analysis:

@include(shared/_mobile-slot-types.txt)

**Systematic Inquiry Process (per sink):**

1. **Identify the Sink:** Record exact function call, file:line, enclosing method
2. **Label the Slot Type:** Using the slot type system above, classify what position
   the data occupies (e.g., CP-selection, WV-loadUrl, SP-value, FILE-path)
3. **Trace Backward to Source:** Follow the data from the sink backward through:
   - Variable assignments
   - Method parameters
   - Return values from other methods
   - Intent extras received
   - User input from UI fields
   - Data from network responses
4. **Document the Data Flow Path:** Record the full chain:
   Source → [Transform1] → [Transform2] → [Sanitizer?] → [Concat?] → Sink
5. **Identify Sanitization:** If any sanitization exists on the path:
   - Record sanitizer name, file:line, and what it does
   - Determine if it MATCHES the slot type (refer to matching rules above)
   - Flag any post-sanitization mutations (concat, format, append)
6. **Make the Call:**
   - Sanitizer matches slot AND no post-sanitization mutation → SAFE
   - No sanitizer → VULNERABLE
   - Sanitizer exists but mismatches slot type → VULNERABLE
   - Post-sanitization mutation detected → VULNERABLE
7. **Score Confidence:** HIGH, MEDIUM, or LOW per the scoring definitions

**Path Forking Rule:** If a single source variable flows to MULTIPLE sinks
(e.g., userInput → ContentProvider query AND userInput → Log.d), treat each
route as a SEPARATE and INDEPENDENT path for analysis. Each path gets its own
slot type, sanitization check, and vulnerability classification.
