## The 9-Point Mobile Authentication Checklist

Every authentication implementation MUST be evaluated against ALL 9 points. This
is not optional — skipping any point creates a blind spot the exploit agent cannot
recover from.

### Point 1: Transport Security
- Are credentials transmitted over HTTPS exclusively?
- Is certificate pinning enforced on authentication endpoints?
- Can a MITM intercept login credentials or tokens in transit?
- Check: Retrofit/OkHttp base URL for auth calls (HTTP vs HTTPS)
- Check: Pinning configuration specifically for auth domain(s)

### Point 2: Rate Limiting and Brute-Force Protection
- Does the server enforce rate limiting on login attempts?
- Is there client-side lockout after failed attempts?
- Is there CAPTCHA or progressive delay?
- Check: Login API response after repeated failures (via Appium + mitmproxy)
- Check: Client-side attempt counter (bypassable via Frida)
- Note: Client-side-only rate limiting = no real protection (Frida bypass trivial)

### Point 3: Session and Token Management
- Token type: JWT, session cookie, custom bearer, OAuth2 access+refresh?
- Token storage location: SharedPreferences, EncryptedSharedPreferences, Keystore, memory?
- Token expiry: What is the lifetime? Is it enforced server-side?
- Refresh token rotation: Does the server issue a new refresh token on use?
- Token revocation: Does logout invalidate the token server-side? Or just delete locally?
- Check: Decode JWT — inspect claims, expiry, signing algorithm (none? HS256 with weak key?)
- Check: After logout, replay old token — does server still accept it?

### Point 4: Biometric Authentication — CryptoObject vs Boolean
**This is the most commonly broken auth pattern on Android.**

- **SECURE (CryptoObject):** BiometricPrompt.authenticate(cryptoObject) ties biometric
  success to a cryptographic operation. The Keystore key requires biometric authentication
  to use, so spoofing the callback does not help — the key operation will fail.
  ```java
  // SECURE — crypto-bound biometric
  KeyGenerator.getInstance("AES", "AndroidKeyStore")
    .init(new KeyGenParameterSpec.Builder("auth_key", PURPOSE_ENCRYPT | PURPOSE_DECRYPT)
      .setUserAuthenticationRequired(true)
      .build());
  Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
  cipher.init(Cipher.ENCRYPT_MODE, keyStore.getKey("auth_key", null));
  biometricPrompt.authenticate(promptInfo, new CryptoObject(cipher));
  ```

- **VULNERABLE (Boolean-only):** BiometricPrompt callback just sets a boolean flag or
  navigates to the next screen. Frida can hook the callback and call onAuthenticationSucceeded()
  directly, bypassing biometric entirely.
  ```java
  // VULNERABLE — boolean-only biometric
  biometricPrompt.authenticate(promptInfo); // No CryptoObject!
  // In callback:
  onAuthenticationSucceeded(result) { startActivity(new Intent(this, HomeActivity.class)); }
  ```

- **Detection:** Search for `BiometricPrompt.authenticate()` — does it take a CryptoObject
  parameter? If not, it is boolean-only and bypassable.

### Point 5: Local Auth Bypass via Direct Activity Launch
**The second most commonly broken auth pattern on Android.**

- Can protected activities be launched directly without going through login?
  ```bash
  # Try launching every protected activity directly
  adb shell am start -n {{PACKAGE_NAME}}/.DashboardActivity
  adb shell am start -n {{PACKAGE_NAME}}/.ProfileActivity
  adb shell am start -n {{PACKAGE_NAME}}/.SettingsActivity
  adb shell am start -n {{PACKAGE_NAME}}/.AdminActivity
  adb shell am start -n {{PACKAGE_NAME}}/.PaymentActivity
  ```
- Does the activity check auth state in `onCreate()` / `onResume()`?
- Is the check server-side (API call fails without token) or client-side only
  (if/else on a local flag)?
- Client-side check with local flag = bypassable via Frida (set flag to true)

### Point 6: Client-Side vs Server-Side Authorization Checks
- **Client-side only:** App checks `isAdmin` flag locally before showing admin UI.
  Bypassable via Frida hook on the flag check or direct activity launch.
- **Server-side only:** API returns 403 for unauthorized requests. Client shows
  error. Secure but verify no data leaks in error responses.
- **Hybrid:** Both client and server enforce. Most secure.
- **Missing:** Neither client nor server checks. Critical vulnerability.

Map EVERY protected feature to its authorization enforcement point:

| Feature | Client Check | Server Check | Bypass Risk |
|---------|-------------|-------------|-------------|
| Admin panel | isAdmin flag | API role check | LOW (server enforced) |
| Profile edit | isLoggedIn | Bearer token required | LOW |
| Premium content | isPremium | No server check | HIGH (Frida bypass) |

### Point 7: Credential Storage Location
- Passwords stored locally? (Should NEVER be stored, even hashed)
- Auth tokens in plaintext SharedPreferences? (Should use EncryptedSharedPreferences)
- Refresh tokens in Keystore? (Best practice)
- API keys hardcoded in source? (Extractable from APK)
- OAuth client_secret in APK? (Should be server-side only — public clients use PKCE)

### Point 8: Root Detection Gating Auth Flows
- Does the app implement root detection? (SafetyNet/Play Integrity, custom checks)
- Is root detection a gate for sensitive auth operations (payment, transfer)?
- Can root detection be bypassed? (Frida hooks on detection methods)
- Is root detection client-side only? (Always bypassable)
- **Note:** Missing root detection is ONLY a finding if the app handles financial,
  health, or high-value authentication data.

### Point 9: OAuth State/Nonce Validation
- If OAuth2/OIDC is used:
  - Is the `state` parameter generated and validated? (CSRF protection)
  - Is a `nonce` used in OIDC flows? (Replay protection)
  - Is PKCE (code_verifier/code_challenge) used? (Required for public clients)
  - Is the redirect_uri validated strictly? (No wildcard or open redirect)
  - Is `code_challenge_method` set to `S256` (not `plain`)?
- If custom OAuth: Are tokens exchanged over HTTPS? Is the token endpoint authenticated?

## Auth Vulnerability Types

Classify each finding into one of these types:

| Type | Description | Typical Impact |
|------|-----------|---------------|
| **biometric_bypass** | Boolean-only BiometricPrompt without CryptoObject | Full auth bypass on device |
| **activity_launch_bypass** | Protected activity launchable without auth | Access to protected features |
| **client_side_auth_only** | Auth check only in client code, no server enforcement | Complete auth bypass via Frida |
| **weak_session_mgmt** | No expiry, no rotation, no server-side revocation | Persistent unauthorized access |
| **token_replay** | Logged-out token still accepted server-side | Account access after logout |
| **credential_exposure** | Plaintext credential storage (SP, files, logs) | Credential theft |
| **missing_rate_limit** | No brute-force protection on login endpoint | Credential stuffing viable |
| **oauth_state_missing** | No state/nonce in OAuth flow | CSRF/replay on auth flow |
| **insecure_password_reset** | Weak reset flow (predictable token, no expiry) | Account takeover |
| **root_detection_bypass** | Root detection present but bypassable | Sensitive ops on rooted device |

### Step 2: Auth Flow Mapping (Static)

Read the decompiled source and trace each authentication flow end-to-end:

1. **Login flow:** UI input → validation → API call → token reception → token storage
2. **Session resumption:** App launch → token check → API validation → grant/deny
3. **Biometric flow:** BiometricPrompt → callback → CryptoObject or boolean → access
4. **Logout flow:** UI trigger → local token deletion → server revocation (or not)
5. **Password reset:** Trigger → email/SMS → reset token → new password → confirmation

For each flow, document:
- Entry point (Activity class, method)
- Validation logic (what checks are performed, where)
- API calls (endpoints, request/response format)
- Token handling (type, storage, expiry)
- Error handling (what happens on failure)

### Step 3: Runtime Verification

**Biometric bypass test:**
```javascript
Java.perform(() => {
  // Hook BiometricPrompt.authenticate to check for CryptoObject
  const BiometricPrompt = Java.use('androidx.biometric.BiometricPrompt');
  BiometricPrompt.authenticate.overload(
    'androidx.biometric.BiometricPrompt$PromptInfo'
  ).implementation = function(info) {
    console.log('[AUTH] BiometricPrompt.authenticate() WITHOUT CryptoObject — BYPASSABLE');
    return this.authenticate(info);
  };
  BiometricPrompt.authenticate.overload(
    'androidx.biometric.BiometricPrompt$PromptInfo',
    'androidx.biometric.BiometricPrompt$CryptoObject'
  ).implementation = function(info, crypto) {
    console.log('[AUTH] BiometricPrompt.authenticate() WITH CryptoObject — SECURE');
    return this.authenticate(info, crypto);
  };

  // Attempt callback spoofing for boolean-only biometric
  const AuthResult = Java.use('androidx.biometric.BiometricPrompt$AuthenticationResult');
  // If no CryptoObject, we can forge a successful result
});
```

### Step 4: Score Confidence

- **HIGH:** Complete auth flow traced, bypass demonstrated at runtime (direct activity
  launch succeeds, biometric spoofed via Frida, token replay accepted by server).
  Clear impact: unauthorized access to protected data or functionality.

- **MEDIUM:** Auth weakness identified in code (boolean biometric, client-side check)
  but runtime verification incomplete (server behavior uncertain, couldn't trigger
  all code paths). Or: token storage insecure but token contents unclear.

- **LOW:** Suspicious auth pattern but purpose unclear, or weakness only exploitable
  under unusual conditions (specific device state, race condition). Or: missing a
  security feature (root detection) for an app that may not require it.

## False Positives to Avoid (Auth-Specific)

### Activity Launch False Positives
- Activity launches but shows empty state / "please log in" message → NOT a bypass
- Activity launches but all API calls fail with 401 → server-side enforced, LOW risk
- Deep link handler launches then immediately redirects to login → SAFE

### Biometric False Positives
- BiometricPrompt with CryptoObject AND Keystore key with setUserAuthenticationRequired →
  SAFE (even if callback is hooked, crypto operation will fail without real biometric)
- App uses biometric only as convenience unlock (no sensitive operation gated) → LOW risk

### Token Storage False Positives
- Token in SharedPreferences but app targets API 23+ and uses full-disk encryption →
  reduces risk (still report but note mitigation)
- Refresh token absent (only access token with short expiry) → session management may
  be acceptable depending on expiry duration

### Root Detection False Positives
- Missing root detection for a news reader / calculator / utility app → NOT a finding
  (only report for apps handling financial, health, or auth-sensitive data)

### OAuth False Positives
- Missing state parameter in OAuth flow handled entirely by a first-party auth server
  on the same domain → reduced risk (still note, but lower severity)
