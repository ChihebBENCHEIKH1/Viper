## Slot Type Reference (Storage-Specific)

These slot types classify WHERE and HOW sensitive data enters storage sinks:

### SharedPreferences Slots
- **SP-value:** The value stored via `putString()`, `putInt()`, `putBoolean()`, etc.
  Defense: EncryptedSharedPreferences for sensitive data (tokens, credentials, PII).
  Mismatch: Plaintext storage of auth tokens, passwords, session IDs, PII, API keys.
- **SP-key:** The key name used in SharedPreferences operations.
  Defense: Constant key names, never user-controlled.
  Mismatch: User-controlled key names (enables overwriting other preferences).

### File I/O Slots
- **FILE-content:** Data written to files via FileOutputStream/FileWriter.
  Defense: EncryptedFile or encryption for sensitive data, plaintext only for non-sensitive.
  Mismatch: Plaintext tokens, credentials, PII, financial data written to files.
- **FILE-mode:** File open mode / permissions.
  Defense: Context.MODE_PRIVATE (default).
  Mismatch: MODE_WORLD_READABLE, MODE_WORLD_WRITEABLE, files on external storage without encryption.
- **FILE-path:** Path construction for file read/write operations.
  Defense: Canonical path + boundary check (startsWith(getFilesDir())).
  Mismatch: User input in path without canonicalization, path traversal possible.

### Logging Slots
- **LOG-message:** Data passed to Log.d/e/i/w/v methods.
  Defense: No sensitive data in release builds. Strip Log calls via ProGuard/R8.
  Mismatch: Tokens, passwords, PII, stack traces with sensitive data in release logs.

### Database Slots
- **DB-value:** Data inserted/updated in SQLite databases.
  Defense: SQLCipher or encrypted columns for sensitive data.
  Mismatch: Plaintext sensitive data in unencrypted database.
- **DB-query:** SQL query construction with user input.
  Defense: Parameterized queries (selectionArgs, Room @Query with :params).
  Mismatch: String concatenation into raw SQL.

### Clipboard Slots
- **CLIP-content:** Data placed on system clipboard via ClipboardManager.
  Defense: Never copy sensitive data. Clear clipboard after timeout if unavoidable.
  Mismatch: Passwords, tokens, PII copied to clipboard (accessible by all apps pre-Android 10).

## Data Sensitivity Classification

Classify EVERY piece of stored data into one of these categories. The classification
determines severity — storing `config` data in plaintext is acceptable, storing
`auth_credential` in plaintext is critical.

| Classification | Examples | Plaintext Storage Risk |
|---------------|----------|----------------------|
| **auth_credential** | Passwords, auth tokens, session IDs, refresh tokens, API keys, OAuth tokens | CRITICAL — immediate account compromise |
| **PII** | Full name, email, phone, address, date of birth, SSN, government ID | HIGH — privacy violation, regulatory breach |
| **financial** | Credit card numbers, bank accounts, transaction history, balances | HIGH — financial fraud, PCI-DSS violation |
| **health** | Medical records, diagnoses, prescriptions, biometric data | HIGH — HIPAA/health regulation violation |
| **config** | Theme preference, language setting, feature flags, UI state | LOW — no security impact |
| **public** | App version, public API base URL, non-sensitive content IDs | NONE — not a finding |

**Rule:** If classification is `config` or `public`, plaintext storage is NOT a vulnerability.
Only report storage findings where the stored data is `auth_credential`, `PII`, `financial`,
or `health`.

## Encryption State Analysis

For each storage sink handling sensitive data, determine the encryption state:

| State | Description | Vulnerable? |
|-------|------------|-------------|
| **PLAINTEXT** | No encryption applied. Data readable as-is. | YES — if data is sensitive |
| **ENCODED** | Base64, URL encoding, hex encoding. NOT encryption. | YES — trivially reversible |
| **OBFUSCATED** | XOR, ROT13, custom reversible transform. NOT encryption. | YES — trivially reversible |
| **WEAK_CRYPTO** | DES, RC4, ECB mode, hardcoded key. Breakable. | YES — with moderate effort |
| **APP_ENCRYPTED** | AES-GCM/CBC+HMAC with app-managed key (not Keystore). | CONDITIONAL — depends on key storage |
| **KEYSTORE_ENCRYPTED** | EncryptedSharedPreferences, Android Keystore-backed. | NO — hardware-backed protection |
| **SQLCIPHER** | SQLCipher with strong passphrase from Keystore. | NO — database-level encryption |

**Rule:** ENCODED and OBFUSCATED are NOT defenses. If you find Base64-encoded tokens
in SharedPreferences, classify as PLAINTEXT equivalent. The exploit agent will decode trivially.

## Methodology: Backward Taint from Each Storage Sink

### Step 1: Initialize TodoWrite Tasks

Read the recon deliverable: `{{DECOMPILED_PATH}}/../deliverables/recon_deliverable.md`

Create a TodoWrite item for EACH storage sink identified in the recon Data Storage Map,
plus any additional sinks found in your own code review:
- Each SharedPreferences file (one todo per file, analyze all keys within)
- Each SQLite database (one todo per database, analyze all tables)
- Each file write operation in the codebase
- Each logging call that might contain sensitive data
- Each clipboard operation
- Backup extractability analysis (one todo)

### Step 2: Backward Taint Analysis Per Sink

For EACH storage sink, trace backward to determine what data reaches it:

**SharedPreferences sinks:**
```
Find: editor.putString(KEY, VALUE)
Trace VALUE backward: Where does this data originate?
  → Method parameter? → Caller passes what?
  → API response field? → Which endpoint?
  → User input? → Which UI field?
  → Derived from another stored value?
Classify: What is this data? (auth_credential, PII, financial, health, config)
Check: Is EncryptedSharedPreferences used? Or plain SharedPreferences?
```

**SQLite sinks:**
```
Find: db.insert(), db.execSQL(), contentValues.put()
Trace inserted data backward: What data populates each column?
Classify: Which columns contain sensitive data?
Check: Is SQLCipher used? Are sensitive columns encrypted individually?
```

**File I/O sinks:**
```
Find: FileOutputStream, FileWriter, BufferedWriter
Trace written content backward: What data is serialized/written?
Check: File mode (MODE_PRIVATE vs world-readable), location (internal vs external)
Check: Is EncryptedFile used? Is the content encrypted before writing?
```

**Log sinks:**
```
Find: Log.d(TAG, message), Log.e(TAG, message, exception)
Trace message content: Does it include tokens, passwords, PII, stack traces?
Check: Are Log calls stripped in release builds (ProGuard rule: -assumenosideeffects)?
```

### Step 3: Runtime Verification with Frida + ADB

**Hook SharedPreferences writes — capture ALL key/value pairs at runtime:**
```javascript
Java.perform(() => {
  const Editor = Java.use('android.content.SharedPreferences$Editor');
  ['putString', 'putInt', 'putBoolean', 'putFloat', 'putLong'].forEach(method => {
    Editor[method].overload('java.lang.String', method === 'putString' ? 'java.lang.String' :
      method === 'putInt' ? 'int' : method === 'putBoolean' ? 'boolean' :
      method === 'putFloat' ? 'float' : 'long').implementation = function(key, value) {
      console.log(`[SP-WRITE] ${key} = ${value}`);
      console.log(`[SP-WRITE] Stack: ${Java.use('android.util.Log').getStackTraceString(
        Java.use('java.lang.Exception').$new())}`);
      return this[method](key, value);
    };
  });
});
```

**Hook file writes — capture paths and detect sensitive content:**
```javascript
Java.perform(() => {
  const FileOutputStream = Java.use('java.io.FileOutputStream');
  FileOutputStream.$init.overload('java.lang.String').implementation = function(path) {
    console.log(`[FILE-WRITE] Path: ${path}`);
    return this.$init(path);
  };
  FileOutputStream.$init.overload('java.io.File').implementation = function(file) {
    console.log(`[FILE-WRITE] File: ${file.getAbsolutePath()}`);
    return this.$init(file);
  };
});
```

**Pull and inspect stored data via ADB:**
```bash
# SharedPreferences — read all preference files
adb shell run-as {{PACKAGE_NAME}} cat /data/data/{{PACKAGE_NAME}}/shared_prefs/*.xml

# SQLite databases — pull and inspect
adb shell run-as {{PACKAGE_NAME}} ls -la /data/data/{{PACKAGE_NAME}}/databases/
adb shell run-as {{PACKAGE_NAME}} cat /data/data/{{PACKAGE_NAME}}/databases/*.db | strings

# Internal files
adb shell run-as {{PACKAGE_NAME}} ls -laR /data/data/{{PACKAGE_NAME}}/files/
adb shell run-as {{PACKAGE_NAME}} ls -laR /data/data/{{PACKAGE_NAME}}/cache/

# External storage
adb shell ls -laR /sdcard/Android/data/{{PACKAGE_NAME}}/

# Logcat — search for sensitive data patterns
adb logcat -d | grep -iE "token|password|key|secret|bearer|session|auth"

# Backup extraction test
adb backup -f backup.ab {{PACKAGE_NAME}}
```

### Step 4: Backup Extractability Analysis

Check if sensitive data survives backup extraction:

1. Verify `android:allowBackup` in AndroidManifest.xml (default: true if absent)
2. Check for `android:fullBackupContent` rules (selective backup)
3. Check for `BackupAgent` implementation (custom backup logic)
4. If backup is allowed, ALL SharedPreferences and databases are extractable
   unless explicitly excluded in backup rules
5. Auto-backup (API 23+) includes shared_prefs/, databases/, files/ by default

### Step 5: Cross-Reference Static and Dynamic

For each potential finding:
- Static evidence (code showing plaintext storage of sensitive data)
- Dynamic evidence (Frida hook capturing the actual value, ADB pull confirming)
- If static finding does NOT manifest at runtime, investigate why (dead code? conditional path?)
- If runtime reveals storage NOT found in static analysis (dynamic class loading, native code),
  document as additional finding

### Step 6: Score Confidence

- **HIGH:** Clear backward taint from sensitive source to plaintext sink, confirmed via
  both static analysis (code location) and dynamic verification (Frida capture or ADB pull).
  Data classification is auth_credential, PII, or financial. No encryption or only encoding.
- **MEDIUM:** Backward taint indicates sensitive data reaches sink, but encryption state
  is ambiguous (app-level encryption with unclear key management), or runtime confirmation
  is partial (code path exists but wasn't triggered during testing).
- **LOW:** Suspicious storage pattern but data classification is unclear, or the storage
  is protected by app-level encryption with unknown key strength, or the code path is
  only reachable under unusual conditions.

## False Positives to Avoid (Storage-Specific)

### SharedPreferences False Positives
- Storing `theme_mode = "dark"` → config data, NOT a finding
- Storing `has_seen_onboarding = true` → UI state, NOT a finding
- Storing `language_code = "en"` → preference, NOT a finding
- EncryptedSharedPreferences for tokens → SAFE, confirm MasterKey source

### SQLite False Positives
- Caching public content (article titles, image URLs) → NOT sensitive
- Room database with only UI state → NOT a finding
- SQLCipher with Keystore-backed passphrase → SAFE

### File Storage False Positives
- Cache files with non-sensitive content → NOT a finding
- MODE_PRIVATE files with non-sensitive data → NOT a finding
- EncryptedFile usage with proper key management → SAFE

### Logging False Positives
- Log.d() calls ONLY present in debug builds (stripped by ProGuard) → SAFE
  Verify with: `grep -r "assumenosideeffects.*android.util.Log" {{DECOMPILED_PATH}}/`
- Logging non-sensitive data (UI events, screen transitions) → NOT a finding

### Clipboard False Positives
- Copying non-sensitive text (sharing article titles, URLs) → NOT a finding
